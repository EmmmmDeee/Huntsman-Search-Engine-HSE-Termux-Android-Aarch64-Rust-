- A correlation rule whose first `type` match names a type in the wrong letter case (`value: emailaddr`) is now refused as `correlation rule r: unknown type emailaddr`, the way a type that does not exist is. Before, it loaded and `scans rules` exited 0, but it never matched an `EMAILADDR` element, since rules match types exactly as Spiderfoot does, and `not emailaddr` kept every element.
- `scans rules --rules PATH`, `scans` and `serve` now name a rules path that exists but cannot be listed (a file, or a directory without read permission), for example `scans: correlation rule ./r.yaml: Not a directory (os error 20)`, and `scans rules` exits 65. Before, the path was taken for a missing directory: only the shipped rules ran, nothing was said and `scans rules` exited 0. A missing directory still adds nothing, silently.
- A rules directory holding more than 500 `*.yaml` files is now named with `N rule files; only the first 500 are read`. Before, the files after the 500th were skipped without a word.
- A correlation rule's `subnet` match now reads a block written with a bare slash and no prefix (`203.0.113.7/`) as no block at all, as Spiderfoot's `netaddr` does. Before, it was read as the single address `203.0.113.7/32`. The match now uses the same CIDR parser as the rest of Huntsman, so every well-formed block or address matches as before.
