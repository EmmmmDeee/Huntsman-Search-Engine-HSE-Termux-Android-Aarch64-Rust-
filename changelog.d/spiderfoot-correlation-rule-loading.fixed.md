- A correlation rule's `exact` match on `type`, `source.type`, `child.type` or `entity.type` that names a catalogued type in the wrong letter case (`value: emailaddr`) is now refused as `correlation rule r: type emailaddr is written EMAILADDR`, and a later match naming a type that is not catalogued as `correlation rule r: unknown type NOT_A_TYPE`, as a rule's first `type` match already was. Before, such a rule loaded and `scans rules` exited 0, but the match never matched, since rules match types exactly as Spiderfoot does, and `not emailaddr` kept every element.
- `scans rules --rules PATH`, `scans` and `serve` now name a rules path that exists but cannot be listed (a file, or a directory without read permission), for example `scans: correlation rule ./r.yaml: Not a directory (os error 20)`, and `scans rules` exits 65. Before, the path was taken for a missing directory: only the shipped rules ran, nothing was said and `scans rules` exited 0. A missing directory still adds nothing, silently.
- A rules directory holding more than 500 `*.yaml` files is now named with `N rule files; only the first 500 are read`, and `scans rules` exits 65. The files after the 500th in name order are still not read; before, they were skipped without a word.
- `serve` prints each rule error as `scans rules` does, `serve: correlation rule RULE: REASON`, on one line with control characters escaped (RULE is the file's path, or the rule's id when the file was read but the rule could not be loaded). Before, it printed `serve: correlation rule RULE is not used: REASON`, unescaped, which was wrong for a directory past the 500-file limit, whose first 500 files are used.
- A correlation rule's `subnet` match now reads a block written with a bare slash and no prefix (`203.0.113.7/`) as no block at all, as Spiderfoot's `netaddr` does. Before, it was read as the single address `203.0.113.7/32`. The match now uses the same CIDR parser as the rest of Huntsman, so every well-formed block or address matches as before.
