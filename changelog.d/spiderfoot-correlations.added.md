- Run Spiderfoot 4.0's 37 correlation rules on every saved scan, beside Huntsman's own. The rules are Spiderfoot's YAML, embedded unchanged under `src/correlations/spiderfoot` (MIT), and run by `sf_correlate`, a Rust port of Spiderfoot's correlation engine with its collect, refine (`source.`, `child.`, `entity.`), aggregate, analyse (`threshold`, `outlier`, `first_collection_only`, `match_all_to_first_collection`) and headline semantics, read by a dependency-free YAML subset reader (`yaml_lite`) and a linear-time regular-expression engine (`pattern`), so no rule can stall a scan. Beyond Spiderfoot: elements flagged false positive are left out, `publish_collections` is honoured, and a Spiderfoot module name in a rule matches the Huntsman source doing that module's work. Operator rules in `$HUNTSMAN_HOME/correlations` (or `~/.huntsman/correlations`, or `--rules DIR`) replace or disable shipped ones by id. New: `scans rules`, `scans correlate ID` (Spiderfoot's `sf.py -C`), `scans correlations ID -f csv|tsv|json`, and the API's `GET /api/correlationrules`, `POST /api/scans/ID/correlate` and `GET /api/scans/ID/correlations?format=`. A scan correlation now carries its rule's name, origin and logic (Spiderfoot's `rule_logic`), Huntsman's rules gained descriptions (`correlator::rule_catalog`), and a Huntsman correlation's title now says what it found.
