# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
The crate (`huntsman-recon`, version `0.2.0` in `Cargo.toml`) has no stable
release yet; relevant pushes to `main` are built and verified, and a current-head build publishes a `main-<sha7>` pre-release (#672). Superseded builds remain Actions artifacts for their retention window. Release policy: only pre-releases (`main-<sha7>` plus a rolling
`latest`); a stable release needs the owner's explicit approval.

Versions and tags. The `v1.x` tags belong to the legacy `hse` monolith (`v1.41.0` is its latest),
so they say nothing about this crate. `huntsman-recon` is not tagged: a build is identified by its
commit, which `build-sha` and `diagnostics` print, and by its `main-<sha7>` pre-release. The
`0.2.0` in `Cargo.toml` is the development version that `--version` and the HTTP `User-Agent`
report. A stable release needs its own version heading in this file, cut when the owner approves it.

Entries are written as fragments under `changelog.d/` (one file per change, see its README) and
assembled into the sections below by `cargo run --locked -p xtask -- changelog assemble` when a
version heading is cut; `changelog render` shows the assembled file at any time.

## [Unreleased]
- Wire the keyed SeekNow breach/stealer source into the `email`, `username` and name (`people`) lookups. `email ADDR`, `username HANDLE` and `scan NAME` (plus `scan -k email` / `scan -k username`, and the `serve` web lookups that call the same `collect` front-end) now run SeekNow whenever `HUNTSMAN_SEEKNOW_KEY` is set, merging its entities into the report by uid and appending its source outcome. With no key the lookups are unchanged and make no extra request; a configured key always runs, as the project requires of a keyed source, and a SeekNow failure is one outcome row, never an abort. The SeekNow client existed but was reachable only through the standalone `seeknow` subcommand, so a configured key was never spent by a normal lookup. The credential is now built by one shared `seeknow_collector::operator_credential`, used by both the `seeknow` command and the lookup leg. The web UI's own markup and `serve` display handlers (PR #974) are untouched; the web lookups pick up SeekNow transitively because they share `collect`.
- Fix the SeekNow collector dropping enumerated contact fields. One SeekNow record often packs several contacts under indexed keys (`email_1`, `name_2`, `phone_1`); the mapper matched only the bare key name, so every indexed identifier was silently discarded and a record whose only identifiers were `email_1`+`email_2` produced no entities at all. `row_entities` now strips a trailing `_<digits>` index before matching, so the packed identifiers become entities while real field names that end in a non-numeric segment (`email_address`, `street_address`, `machine_id`, `postal_code_11_characters`) are unaffected.
- Add `huntsman-recon doctor` and `huntsman-recon fix`. `doctor` checks the binary on PATH, its build SHA against `~/.huntsman/installed-revision`, the state directory, `~/.huntsman.env` (never its values), configured keys (`--probe` tests them live), ledgers, the install acceptance, a running `serve` (`doctor serve` probes the page, its CSP script hash and offline analysis), free disk, the build cache and the Termux paths, and names the fix for each problem; it exits 78 when a check fails. `fix` makes the repairs that can be undone and checks again.
- Fix the main-channel release race where a queued build could become historical before `gh release create --target <sha>` and fail with GitHub's built-in workflow token. Publication now uses a draft created from the live main head, verifies its tag exactly, and discards a raced draft rather than failing or publishing the wrong commit.

### Added

- The serve page is laid out as Spiderfoot 4.0's web UI over the saved scans: Scans (list, status filter, stop, re-run, delete and JSON export of one or several), New Scan (by use case or by required data type, with the modules listed and marked when they need a key), a scan's Summary, Correlations, Browse (full, unique and Discovery Path back to the target), Graph, Scan Settings (options, what each honoured, the lookup report), Log, wildcard search, CSV/TSV/JSON/GEXF export and false-positive flags, and Settings (each module's category, access and whether its key is set). `serve` now answers `/api/scans…`, `/api/eventtypes` and `/api/settings` from the scan API behind the lookup guards, each call on its own 4 MiB-stack worker, and recovers scans a stopped server left running as `ABORTED`. A running scan is polled at 1, 2, 4 then 5 s, and the page never calls the API before the first health answer says whether a token is needed. The page is about 82 KB with no library, inside a 96 KiB budget; `tests/web_ui.rs` checks about 60 fields it reads against a real `ScanApi` and that every export it offers is one the API writes, and the CI browser check runs a scan end to end on the binary, including after a restart.
- Saved Spiderfoot-style scans. `scans run TARGET` runs the lookup the target routes to and saves its report, every entity with its evidence, every source outcome, Spiderfoot data elements and HIGH/MEDIUM/LOW/INFO correlations under an id in `~/.huntsman/scans` (`$HUNTSMAN_HOME/scans`); `scans list|show|summary|elements|correlations|log|export|fp|rerun|delete|types` read and manage them. The data elements use Spiderfoot 4.0's own 172-type catalogue (`sf_types`, from its `tbl_event_types`) plus Huntsman's `HSE_` types, typed against the target the way Spiderfoot types its events (`INTERNET_NAME` vs `AFFILIATE_INTERNET_NAME` vs `CO_HOSTED_SITE`, `TCP_PORT_OPEN`, `VULNERABILITY_CVE_*`, `MALICIOUS_*`, `EMAILADDR_COMPROMISED`, `BGP_AS_MEMBER`, `GEOINFO`...) with each element linked to the one it came from. Exports are Spiderfoot's CSV/TSV/JSON layout plus GEXF; a scan interrupted by a stopped process reads `ABORTED` instead of running forever. `scan_api` answers Spiderfoot's web API (`scanlist`, `startscan`, `scanstatus`, `scansummary`, `scaneventresults[unique]`, `scancorrelations`, `scanlog`, `scanviz`, exports, `stopscan`, `scandelete`, `rerunscan`, `resultsetfp`, `eventtypes`, settings status) as `/api/scans...` for `serve` to mount. `sf -T` now lists the whole catalogue, `sf -t` accepts any of its types, and `sf -s` rows are the same typed elements.
- `serve --history DIR` bridges the web UI's offline analysis to the saved scan artifacts in DIR, as `correlate --history` does for one artifact. Each `/api/analyze` report carries `cross_scan`: `null` without a history, `"None"` when no saved scan shares an entity, and otherwise the bridges and the scans they reach. `serve` refuses to start on a history it cannot read or that holds a malformed artifact, with `correlate`'s exit codes. The bridge analysis had no production caller before, so the web view never showed a cross-scan link. An operator's seed bridges now as well: every seed carries 0.25, below the 0.45 a finding needs, so seeds were silently dropped from the bridge. `Evidence::is_operator_seed` is the one test for a seed, and the seed role is `SEED_EVIDENCE_ROLE`.
- Four more keyless sources: XposedOrNot (`email`: the names of public breaches that included the address, never record content, grouped with the other breach evidence), StopForumSpam (`email`, `ip`: forum-spam report count, last report, confidence and Tor-exit flag), Robtex (`ip`: BGP route, origin AS and passive DNS names; `domain`: the addresses, name servers and mail exchangers passive DNS saw) and HackerTarget (`domain`: hosts and their addresses; `ip`: domains hosted on the address; `HUNTSMAN_HACKERTARGET_KEY` raises the 50-a-day limit). Their names and addresses become pivots.
- Four more sources that need no key, so every lookup gains them at once: AlienVault OTX (`ip`, `domain`: how many community threat pulses name the indicator, their tags, malware families, adversaries and targeted industries, and OTX's allow-list and Tor-exit validations), urlscan.io (`ip`, `domain`: public page scans involving the indicator, how many urlscan.io judged malicious, and the domains, addresses and networks of those pages as pivots; scanned URLs are not kept because their query strings can carry other people's tokens), IPinfo (`ip`: reverse hostname, origin AS and holder, city, region and country; coordinates and postcode are not kept) and Kickbox Open (`email`: whether the address's domain is a disposable-mail provider; only the domain is sent). Optional free keys raise the first three's limits: `HUNTSMAN_OTX_KEY`, `HUNTSMAN_URLSCAN_KEY`, `HUNTSMAN_IPINFO_KEY`.
- `email ADDR` (and `scan -k email`, `sf` EMAILADDR scans and the web UI's email lookup) and `phone NUMBER` now run the indicator sources too. For an address: IPQualityScore email validation (`HUNTSMAN_IPQS_KEY`: deliverability, fraud score, disposable, leaked, first seen), the Hunter.io verifier (`HUNTSMAN_HUNTER_KEY`: verdict, score, disposable, webmail, accept-all and blocked flags) and Whoxy reverse WHOIS (`HUNTSMAN_WHOXY_KEY`: every domain registered with the address becomes a domain pivot). For a number: IPQualityScore phone validation (line type, carrier as an organisation pivot, VOIP, prepaid, fraud score). Each runs only when its key is set; with no key both lookups are unchanged and make no extra request.
- `network BSSID|LAT,LON|ssid:NAME` looks up a WiFi network, and `scan`, `scan -k network` (aliases `wifi`, `bssid`, `ssid`, `wigle`) and the web UI's new `network` kind reach the same front-end. `scan` infers a BSSID or a coordinate pair; an SSID is free text, so it needs the kind named. A BSSID is classified offline first (IEEE OUI vendor, and whether it is a randomised address). Then WiGLE network search runs when `HUNTSMAN_WIGLE_USER` (the API Name) and `HUNTSMAN_WIGLE_TOKEN` (the API Token) are both set in the environment: a BSSID searches that network, an SSID searches networks with exactly that name, and a coordinate pair searches a box of about 220 m around it, nearest first. A BSSID and a coordinate pair are also searched in WiGLE's Bluetooth database (classic and BLE): each device becomes a MAC entity with its radio, device class and name (kept as an attribute, never a pivot, since it often names its owner) and the report adds `wigle_bluetooth_devices=N` and `wigle_bluetooth` rows; that is a second daily query. Each network becomes a BSSID entity with its SSID, encryption, channel, trilaterated position, first and last sighting and the street address WiGLE gives the position, and its SSID and position become pivots. The report ends with `wigle_networks=N` and one `wigle_network` row per network. One page of 100 networks is read and a larger answer is marked partial. Without both credentials no request is made and the leg reports `auth_required`; a rejected credential, the daily query limit or a failed query is reported as such, never as a zero. `credential-status --probe` checks the WiGLE credentials against WiGLE's own-profile endpoint, which spends no search query, and keeps nothing from the profile. `provider_credentials::wigle_credential` is the one place the two slots become a credential, for searches and the probe alike. The credentials travel as HTTP Basic auth only to `https://api.wigle.net` and redirects are not followed; the fetch layer gained a Basic style that scrubs both the pair and its encoded form from diagnostics. This makes `rf::RfSource::WigleApi`, until now unreachable, the source of every WiGLE sighting. The endpoint and fields follow WiGLE's published Swagger document and are not yet verified against a live account.
- The web UI's kind picker now lists `domain`, which was reachable only by `auto` inference, and a test ties the picker and the `scan` usage to `ScanKind::ALL` so a new kind cannot be left out of either.
- `email ADDR`, `scan -k email` and the web UI's email lookup also ask Duolingo and keys.openpgp.org, the two keyless email checks from Epieos's module list that answer honestly. Duolingo's user endpoint filters by address; a matching account adds its handle, profile URL and location, with the account id, creation time, paid plan and whether a phone number is on it as evidence. keys.openpgp.org publishes a user ID only after its owner confirms the address, so a key found for the address adds every other confirmed address and the name on that key, with its fingerprint and creation time. Each source reports its own outcome row (`duolingo`, `openpgp_keys`), one source's failure leaves the others' results in place, an empty answer is a validated zero and a changed response shape is drift, never a zero. Proton Mail's key server is not used: it returns a key for any `@proton.me` address, registered or not. Both requests are paced by the shared per-host circuit breaker. Response shapes were recorded from the live services on 2026-10-14.
- Netlas (keyless; `HUNTSMAN_NETLAS_KEY` raises the limit), abuse.ch URLhaus (`HUNTSMAN_ABUSECH_KEY`) and SecurityTrails subdomains (`HUNTSMAN_SECTRAILS_KEY`, `domain` only) join the indicator sources. `api_leg` gains a form-encoded POST for URLhaus. Netlas WHOIS contact phones and postal addresses are never decoded.
- Six more indicator sources run in `ip` and `domain` (and so in `scan` and the web UI): Shodan host and DNS (`HUNTSMAN_SHODAN_KEY`), Pulsedive (keyless, `HUNTSMAN_PULSEDIVE_KEY` raises the limit), LeakIX (`HUNTSMAN_LEAKIX_KEY`), abuse.ch ThreatFox (`HUNTSMAN_THREATFOX_KEY`), IPQualityScore (`HUNTSMAN_IPQS_KEY`, `ip` only) and Whoxy WHOIS (`HUNTSMAN_WHOXY_KEY`, `domain` only). A set key always runs its source. They share one registry (`indicator_legs::SOURCES`), so a new source is one module and one entry. Shodan and Whoxy take their key only as a query parameter: `fetch` now supports that style, adding the key as the request is sent, dropping any caller-set parameter of that name, never carrying it across an origin change, and scrubbing it, raw and percent-encoded, from diagnostics. Whoxy's and IPQS's HTTP-200 refusals are reported as a rejected key or a plan refusal, never as a zero. LeakIX credentials found on a service and WHOIS street addresses and phone numbers are never decoded.
- `ip ADDRESS` looks up one public IPv4 or IPv6 address, and `scan` routes an address to it (the web UI lists `ip` and `domain` as kinds). Three keyless sources answer: Shodan InternetDB gives open ports, hostnames, CPEs and known CVEs; RIPEstat gives the covering prefix and the origin AS with its holder; GreyNoise Community says whether the address scans the internet or is a known benign service. With `HUNTSMAN_ABUSEIPDB_KEY` set AbuseIPDB adds its abuse confidence and report counts, with `HUNTSMAN_VIRUSTOTAL_KEY` set VirusTotal adds engine verdicts, and `HUNTSMAN_GREYNOISE_KEY` raises GreyNoise's limit. Hostnames, origin AS numbers and their holders become pivots. A private, loopback, link-local, CGNAT, documentation or other non-public address is refused with exit 65 before any request, so it is never disclosed to a provider.
- `domain` adds VirusTotal's verdicts, registrar, creation date and categories when `HUNTSMAN_VIRUSTOTAL_KEY` is set, and the work addresses Hunter.io found published for the domain, with the name, position and confidence Hunter gives them, when `HUNTSMAN_HUNTER_KEY` is set. `phone` adds Numverify's carrier, line type and location when `HUNTSMAN_NUMVERIFY_KEY` (an APILayer key) is set; without it `phone` stays offline. `phone` now prints each source's real outcome instead of `success` for every row.
- Every free-tier leg goes through one request path, `api_leg::get`: the key comes only from the environment, is sent only to its provider's origin in that provider's header, and redirects are not followed. A rejected key, a plan or quota refusal and a rate limit (with the provider's pause) are reported as such, never as a zero; a provider's documented "nothing known" answer is a valid zero. A keyed leg whose key is not set makes no request. `credential-status` lists the AbuseIPDB, GreyNoise, Hunter.io and Numverify slots with where to get each key and its free tier, and `modules` lists the eight new sources.

- `exposure` searches OathNet's breach records when `HUNTSMAN_OATHNET_KEY` is set in the environment, after HIBP and stolen.tax, so `exposure ADDR`, `scan -k exposure` and the web UI's exposure lookup all include it. Each breach database becomes evidence on the address: its `dbname` (which lineage reads, so a database another source relays counts once), record count, the field types its records expose, whether a password or hash is among them, the breach's public title, date and size, and when OathNet indexed the records. The report ends with `oathnet_breaches=N` and one `oathnet_breach` row per database. Usernames and other addresses in the records become pivots; no other record value is kept, so a password, hash, phone number or street address cannot reach the report or a saved ledger. One page of 100 records is read and a larger answer is marked partial. Without the key no request is made and the leg reports `auth_required`; a rejected key, plan, quota or rate limit is reported as such, never as a zero. The key is sent only to `https://oathnet.org` and redirects are not followed. The endpoint and fields follow OathNet's published OpenAPI document and are not yet verified against a live key.

### Changed

- The web UI shows what a lookup found and keeps it. Each entity is listed with its kind, value and confidence, and opens to its tags, every piece of evidence with its source, and the evidence's attributes (built when opened, so hundreds of entities stay cheap; a filter appears past eight). Source rows add the HTTP status, retry-after and the source's own detail. The last lookup and analysis are kept in the tab's session storage, so they come back when Android discards and reloads the tab instead of being run, and paid for, again; nothing is kept past the tab. A running lookup shows its time and can be stopped by pressing the button again. The page follows the phone's light or dark setting until the toggle picks one, colours the browser bar like the app bar, and every text colour now meets WCAG AA in both themes (the light theme's status colours were 2:1). A tab that comes back into view asks only for health (89 bytes instead of 21 KB): the module list and command contract load when Status opens. A stopped server is named, with `huntsman start`, and its return is noticed without a reload. `tools/web-ui-check` drives the page in a phone-sized Chromium with axe-core, and CI's new `web-ui` job runs it; `tests/web_ui.rs` holds the colour, theme, report-field, storage and polling contracts.
- The web UI looks like the HSE console again and asks for no token on the phone. The page (now `src/web_ui.html`) has the console's app bar, locator mark and dark theme (with a light switch), a bottom tab bar for Look up, Analyze and Status on a phone (a top nav from 768 px), panels, summary tiles, outcome chips, and table rows that become labelled cards on a narrow screen. A loopback `serve` needs no token: `HSE_AUTH_TOKEN` is ignored there (it says so on stderr), so the page never asks for one and forgets a token an earlier page stored. A public bind still needs the token, and only then does the page show the token field. The Termux installer stops writing `~/.huntsman/serve.token`, removes the one an earlier install wrote, and the service no longer exports it; `huntsman open` opens the plain address and `doctor`'s advice for a server that asks for a token says a current loopback build needs none. Other websites are still kept out by the `Host` guard and the lookup header; other apps on the phone can reach the loopback API, as before #965.
- A handle that many addresses share costs a search only where it can change a result. The addresses it joins form one component, and every two of them are joined by a relation resting on that one handle, so each pair's pathway is the handle and needs no search for its count. Brokers need no search either, since the direct relation is the strongest path between two such addresses. With one handle on 1,000 addresses, `correlate` took 374 s and now takes about 7 s, with the same correlations. Relation derivation also removes duplicate relations in place instead of copying all of them, so the half-million relations of that group are not copied again.
- Every release build (the phone's `cargo install`, CI's Android cross-build, the Railway container and the issue-fix workflow's xtask builds) uses thin link-time optimisation and strips symbols; the release workflow already ran `llvm-strip` over the published Android asset, and the other builds now match it. On x86_64 with 4 cores the binary shrinks from 8.5 MB to 6.5 MB, `plan` with 256 seeds runs in 11.3 ms instead of 19.3 ms and the graph analysis of 5,000 entities in 345 ms instead of 386 ms (`examples/multihop_bench.rs`, medians, identical checksums); a clean release build takes 102 s instead of 80 s. Panics still unwind, so `serve` keeps answering a failed request with 500. `tests/manifest_policy.rs` holds the profile.
- `plan` and the web UI's analyze view give the same results in a fraction of the time. Now that the analysis runs the relation rules, `plan` with a domain and 255 addresses on it took 19 s, almost all of it in AU-062, AU-063 and AU-070; it now takes 0.26 s. Given the relations of 400 addresses on one domain, those rules took 72 s and now take 0.18 s; for a handle shared by 40 sites they took 24 s and now take 0.43 s; and `analyze_snapshot` on 4,096 entities took 3.4 s and now takes 0.18 s (`examples/multihop_bench.rs`, release build, x86_64; every result is unchanged). One widest-path search from each entity now finds its strongest path to every other entity, where each pair ran its own search over a fresh copy of every relation. Core numbers are computed in linear time, and the pivot ranking runs its breadth-first searches 64 at a time. AU-070 scores brokers over pairs in uid order, so the same scan names the same brokers every run; it followed a hash map's order, which changed from run to run.
- `plan` and the web UI's analysis do less work for the same result. The planner formatted two dispatch ids for every comparison while it sorted the plan; it now formats each id once. Canonical JSON was written from a sorted deep copy of the whole value; it is now written straight from the value, each object's members sorted on the way (`serde_json` already keeps them in order, unless a crate in the build switches on its `preserve_order` feature). A four-seed analysis runs 22.7% fewer instructions and a sixteen-seed one, the most the web UI takes, 15.8% fewer. The outcome and every rendered artifact are byte-identical before and after at 4, 16, 64 and 256 seeds. `json::sorted_value` and `json::from_str_sorted`, which nothing else called, are removed.
- The offline investigation spine is `huntsman-recon plan`. It was a separate `investigate` executable. The prebuilt Termux release ships only `huntsman-recon`, so it could not run the spine, and a source install put a second program named `investigate` on the PATH, unrelated to `huntsman-recon investigate`, which extracts entities from text. `plan [--session-dir DIR] SEED...` and `plan --load-session DIR ID` take the same arguments and print the same lines. Upgrading a source install with `install.sh` removes the old `investigate` program: Cargo 1.87 and later remove a binary that a reinstalled package no longer has. A run whose session cannot be written exits 74, as a lookup's `--save` does, instead of 70; status 70 is no longer used.
- Running `huntsman-recon` with no command prints the help and the usage line to standard error, exits 64 and writes nothing. It used to run `check`, which writes `var/ledger.json`, `var/navigator.json` and `var/stix-bundle.json` into the current directory, so the first thing a new user typed in Termux left `~/var` behind; a script that relied on it must now name `check`. Of the README's offline examples, `check` is the only one that writes without an output option. `tests/readme.rs` now requires every other example to leave the directory it runs in unchanged, byte for byte. `docs/INSTALL.md` starts a new install with `diagnostics` instead of `check` and says where `check` writes, as do `check --help` and the README.
- `search` treats a saved file as a challenge page only when it is an HTML document of at most 32 KiB that carries a challenge signature. Markdown, prose and longer pages that quote a vendor or phrase are now searched. The fetch path keeps its stricter rule.
- `search` matches a query that is one email address or one domain as a whole name. `ada@example.com` no longer matches a document that holds "ada", "example" and "com" apart. A domain still matches its subdomains and the addresses at it.
- Engineering-command role names are neutral titles (for example `CHIEF VISIONARY` and `ECONOMIC OPTIMIZATION LEAD`) instead of the earlier named-figure roles, and the command invariant is `CHIEF VISIONARY -> CHIEF SYSTEMS ARCHITECT -> ALL OTHER SYSTEMS`. Any consumer that keys on the old role `name` values in the JSON output must switch to the new names.
- `search` folds Latin diacritics and keeps combining marks and soft hyphens inside a word (Unicode word rule WB4), so `zurich` finds `Zürich`, `jose` finds `José` and `istanbul` finds `İstanbul`, and decomposed text is no longer split at its marks. The folding is accent-insensitive by design: `schon` and `schön` find each other. It also counts only the query terms, which about halves the time of a search with the same hits and scores (`examples/search_bench.rs`).
- The classifier behind `investigate`, `scan` and the `search` query matches company and street markers as whole words, and only in a value of two or more words; a single word is residual. `Vincent Smith` and `Lincoln Hill` are no longer organisations, and `Broadbent Lee` is no longer an address.
- `investigate` scans spans, not single tokens. A phone number, or an ABN or ACN written as two to four digit groups, is one entity (`+61 412 345 678` used to give four address entities). A street address begins at its street number and ends on its last street word, a capitalised connector such as "The" ends it, and bare digits and digit pairs are no longer addresses or people.
- The name matchers (the ASIC director and person lookups, `au_people` and `people`) ignore case for accented letters and count an initial by letters, not bytes: `Émile` matches `émile`, and `É Lovelace` has no name token. Matching lowercases letter by letter; it does not fold accents or `ß`.
- Exit statuses follow `src/exit.rs` and the README. `serve` exits 66, not 65, when `HSE_AUTH_TOKEN` is blank, or absent on a non-loopback bind (an invalid bind address still exits 65). `seeknow` exits 66, not 77, when its key is not configured (a key that is present but refused still exits 77). `verify` exits 66, not 65, for a missing or unreadable ledger (a malformed ledger or a broken chain still exits 65). A script that keys on these statuses must follow.
- `sources` strips every leading `@` from a username and refuses a value made only of `@` signs or only of dots (exit 65, empty stdout).

### Security

- rustls 0.23.45 → 0.23.46 (lockfile only). The `cargo audit` workflow, run because #933 touched the manifest, flagged the locked version with four advisories published 2026-10-14 and all fixed in 0.23.46: RUSTSEC-2026-0346 (`Debug` impls for client session values expose TLS secrets), -0347 (buffered application data sent to the outer server after ECH rejection), -0348 (Brotli certificate decompression can allocate up to 1 GiB before authentication) and -0349 (an unauthenticated ServerHello can downgrade later connections to classical key exchange). Every HTTPS request the binary makes, DNS over HTTPS included, goes through this crate.

### Removed

- The four async engine crates under `crates/` (`huntsman-core`, `huntsman-storage`, `huntsman-collectors`, `huntsman-pipeline`; about 6,500 lines) and the ten library modules with no caller (`assurance`, `breach`, `diamond`, `diff`, `key_health`, `mediawiki`, `method_actor_stateful`, `method_actors_osint`, `repository_identity`, `trust`; about 3,100 lines) were removed. The root package never depended on the crates, which brought 21 lockfile packages, among them `tokio`, `redb`, `blake3` and `tracing`, that the shipped binary never used, and nothing imported the modules. The shipped `huntsman-recon` binary is unchanged, because nothing it builds depended on them, and the acceptance gate no longer compiles or tests them.

### Fixed
- Adding a source to one lookup kind no longer breaks the build for everyone. The lookup dispatcher `collect` kept growing past clippy's 100-line limit as sources landed (it reached 104 after DeHashed and WiGLE). Each kind now runs in its own function, and `collect` only dispatches.

- The entity-graph GEXF export (`gexf`) wrote C0 control characters from provider text as they were, which XML 1.0 cannot carry, so Gephi refused the file; they are now written as U+FFFD, through the one `gexf::escape_xml` the saved-scan export also uses.
- crt.sh issuer organisations keep a quoted comma. crt.sh prints an issuer as `C=US, O="CLOUDFLARE, INC.", CN=…`, and the issuer parser split on every comma, so the organisation became `"CLOUDFLARE`. No public-CA prefix matched that, so Cloudflare, thawte and every other CA whose name has a comma came out as an "enterprise PKI" organisation pivot, linking unrelated domains as one operator's. The parser now reads the name as RFC 4514 does: a comma or `+` inside double quotes or after a backslash belongs to the value, and quotes and escapes are removed. `SSL Corporation`, the name SSL.com issues under, joins the public CAs.
- AU-002 does not count a username the analysis inferred from an email's local part. An email and the username derived from it made a Critical identity cluster, though the username adds no identity beyond the address it came from. Inferred usernames are left out of that count, so a derived name found on a public profile no longer raises the alert by itself. Usernames that were observed still count, and a test covers each case. The new test fails on the previous code.

Each address it resolves to, mail exchanger, name server, domain its SPF policy includes, DMARC and TLS-RPT report mailbox and TLS-RPT report URL is an entity tied to the domain; the domain lists its addresses under `ip`, its exchangers under `mx` and its name servers under `ns`, carries each TXT, DMARC and TLS-RPT record as evidence and its SPF and DMARC posture as tags. So `--save`, the web UI's entity list and the analysis see them, and two domains on one address give the resolution relation and the shared-hosting rule (AU-110) what they read; before, no live lookup produced an address, so neither fired outside a hand-made artifact. The DNS leg sends through the lookup's own transport instead of opening a second connection, its row counts records, a name with no records is a validated zero and a resolver outage says why instead of an empty count, crt.sh's empty list (no certificates logged for the name) is a validated zero instead of `inconclusive`, a lookup every source answered with nothing prints those zero rows instead of failing with "no results for domain" (exit 69, which the README keeps for no usable response), and a lookup where no source answered says why ("no source answered for domain …: crtsh: no response …", exit 69) instead of "no results", or exits 77 when the egress policy refused a request, as the README's exit codes say.

### Added

- The web UI runs the multi-hop analysis offline. `GET /api/analyze?seeds=…` runs the investigation spine `plan` runs, on up to 16 seeds, one per line, and returns what `plan` prints only as counts: the entities, the links derived between them, the next pivots ranked by how much of the graph each holds together (an email that links a username and a domain is the cut point), the correlations over those links, the seeds left unlinked with what would expand them, and the sources the planner would query next. The page has an analysis form that shows each of these as a table and can download the JSON. Nothing is fetched and no key is spent: the spine is handed no transport. On Termux the server's connection threads have a 256 KiB stack, which the analysis overflows, so each analysis runs on its own 4 MiB-stack worker; a test serves a deliberately deep handler from a connection-sized thread and aborts with a stack overflow if the analysis runs inline. The route is refused cross-site and needs the token when one is set. `tests/serve_analyze.rs` runs it against the shipped binary.
- `tools/headless-fetch/` is an optional operator helper (Node + Playwright) that renders JavaScript challenge pages a plain HTTP client cannot, printing one JSON record per URL for `investigate`. It is deliberately outside the engine binary: the static Termux aarch64 build ships no browser, and the helper bypasses the egress guard, so it is operator-side only and documented as such. It defeats JS challenges but not IP-reputation blocks or captchas.

Before, every networked lookup on such a network failed with an unknown-issuer TLS error and no way to trust the network's CA.
