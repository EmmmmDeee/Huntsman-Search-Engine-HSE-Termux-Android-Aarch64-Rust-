## [Unreleased]

### Fixed

- `wikitree` namesakes no longer raise the subject's exposure score. Every WikiTree "John Smith" merges onto the seed Person by name, and each profile's `born` date was scored by the exposure index as the subject's disclosed DOB. Profile records are now marked `Unverified` in the existing `Evidence.verification` field, and the exposure index does not count an unverified record as the subject's own. Three silent clean negatives are typed too: a seed that does not split into first and last name is a scoped skip, the `limit=10` page is declared truncated against WikiTree's own total, and a private profile is a `private-profile` source Url rather than nothing (REQ-WIKITREE-001 / REQ-WIKITREE-002).
- `hunter_io` no longer reports a domain's employees' LinkedIn / Twitter as the subject's own accounts. A domain search lists everyone Hunter holds at the domain, and tagging those profiles `social-profile` made AU-055 ("the subject's own confirmed accounts", Critical at three platforms) and AU-038 fire on colleagues. They are now `employee-profile` pivots. The one-page answer is declared truncated when Hunter's own `meta.results` count exceeds it, and a full page with no count is declared too (REQ-HUNTER-001 / REQ-HUNTER-002).
- `emailrep` no longer makes every address it answers for VERIFIED. It re-emitted the target at a fixed 0.85, so an undeliverable address, one on a nonexistent domain, or an empty report became top-tier. It now earns `hibp`'s rung (0.70) only when the report observes the address itself (profiles, a breach or leak, behaviour, a first-seen date), and is otherwise an annotation below the presence rung. The credential-leak flag is read under the vendor's documented name, `credentials_leaked`: every leak EmailRep reported had been dropped (REQ-EMAILREP-001 / REQ-EMAILREP-002).
- `au_unclaimed` makes one acceptance decision for a QLD unclaimed-money row, and both the entity pass and the suburb enumeration take it. The suburb pass had its own weaker test and took every row of an organisation search, so the payees on rows CKAN matched by sender were enumerated as the organisation's suburbs. An organisation seed now needs the same company (`util::abn::same_company`, equality after legal-form folding), not a token subset: `"Ford"` no longer claims the individual `"MR JOHN FORD"`, and a different company carrying the seed's words is a tentative `similar-company` lead, not a relative. A joint owner is judged per co-owner, so `"JOHN NGUYEN & MARY SMITH"` is no longer John Smith (REQ-AU-UNCLAIMED-001 / REQ-AU-UNCLAIMED-002).
- The shared curl fallback behind `fetch_json` / `fetch_json_or_404` reads the HTTP status. It ran `curl -s` without `-f` or status capture, so on the Termux / DC IPs where it is the working transport, a 404, 429 or 5xx whose error body decoded as the expected JSON came back as a successful answer: a 404 meant for "absent" became data, and a throttle could read as a clean result for every module on the shared helper. The fallback now answers exactly as the reqwest path does, with the same typed errors and the same breaker decision. The status-blind `util::curl::fetch_json` is deleted, and the write-out contract is locked against the real `curl` binary (REQ-CURL-001).
- `leakix` decodes the shape LeakIX actually sends: capitalised, nullable `Services` / `Leaks` with string ports, per LeakIX's own client and `l9format` schema. It read lowercase keys only, so every real response decoded as two empty lists and every host and domain was reported as having no exposure. A 200 body carrying neither key now fails closed instead of reading as a clean negative, and SSH exposure is read from `protocol` (REQ-LEAKIX-001).
- `pulsedive` follows the vendor's own verdict. A `none` / `very low` risk, which Pulsedive defines as "benign activity", was still tagged `THREAT_INTEL`, raising AU-015's High threat-intel finding. It was also tagged `MALICIOUS` whenever any threat was linked. A benign verdict now carries `pulsedive-benign` and no bad tag, an unassessed or risky one is a `THREAT_INTEL` sighting, and only `high` / `critical` are `MALICIOUS` (REQ-PULSEDIVE-001).
- `THREAT_INTEL_SOURCES`, which decides whose `MALICIOUS` tag AU-004 counts and AU-015 names, had drifted from the modules that emit it: `emailrep` and `pulsedive` were missing. Both are added, and `tests/architecture.rs` now fails when a module tags `MALICIOUS` without being on the list (REQ-THREATSRC-001).
- `registrable_domain` reads the Public Suffix List, vendored verbatim with the list project's own conformance suite run as a unit test (78/78), instead of a 39-entry table with no Vietnamese second level. It answered `com.vn` for every `.vn` commercial domain. As a result, a credentialed redirect from `api.provider.com.vn` to `attacker.com.vn` was judged same-site and replayed the provider key, and the same held for every suffix the table lacked and for shared hosts like `github.io`. AU-118 could never see a Vietnamese impersonation, and AU-110 counted two Vietnamese companies on one IP as one site. A bare public suffix now has no registrable domain (REQ-PSL-001).
- `dns_intel` no longer permutes a registrable apex under a multi-label suffix. For `acme.com.au` it generated and resolved `acme1.com.au`, `dev-acme.com.au` and the like, which are other registrants' domains, and emitted each hit as the target's own subdomain at very high confidence. The gate is now the registrable-domain apex test `srv` and `dkim` already use (REQ-DNSINTEL-001).
- The live-scan registry lock no longer races the release it checks. It asserted the in-flight entry was gone at the instant the scan row read terminal, but the row is written inside the engine's run and the entry is released after the run returns, the order REQ-SCANSTATUS-001 requires. It failed CI on a loaded runner and was reproduced locally (7 failures under CPU contention). It now waits for the release; 60 of 60 runs pass under the same load, and a product that never releases still fails it (REQ-LIVE-001).
- The inter-scan entity cache replays a result with its completeness verdict. It stored entities only and rebuilt every replay with `truncation: None`, so a partial answer from a cached module (`netlas`, `see_know`, `passivetotal`) was reported complete on every re-scan inside its TTL. The cache now stores `{entities, truncation}`. A row archived before the change carries no verdict and is treated as a miss, re-asked once and re-archived, rather than replayed with an invented "complete" (REQ-CACHE-001).
- `asic_banned_orgs` and `asic_business_names` no longer turn a partial CKAN page into a clean negative. The truncation check sat after the no-match return, so a full `limit=100` page of broad free-text hits with no whole-word match, from a search CKAN reported as larger, came back as a complete "not banned" / "no registration", while the real record may have been in the rows never fetched. The page is now declared partial before anything else (REQ-COVERAGE-002).
- `passivetotal` declares its client-side cap. The API takes no limit, so a long-lived domain returns thousands of rows with `totalRecords` equal to what it sent. The old check compared the total with the returned count and could never see the `.take(200)`; `build_entities`' truncation flag was a constant `false`, locked by a test asserting `false`. An IP query's truncation note is now an `IpAddress`, not a `Domain` named after the IP (REQ-COVERAGE-002).
- `dns_axfr` declares a zone transfer it read only part of: the parser's 500-record cap (with the advertised count), or a first message without the zone's closing SOA (RFC 5936), which is how a zone split across several messages arrives and was reported as the complete inventory (REQ-COVERAGE-002).
- `netblock` enumerates an IPv6 block that fits its cap, as its header always claimed for `/120`, and declares a wider block with its exact size through the new `ModuleResult::mark_truncated_of` (a `u128` known total, sharing the one truncation sentence). `wikidata`, `virustotal` and `netblock` now reach the coverage layer; before, their only truncation signal was an entity tag nothing reads. A `tests/architecture.rs` lock requires any module that tags `truncated` to declare it too, with `leakix` exempted because it caps only a displayed port list (REQ-COVERAGE-002).
- `certspotter` follows Cert Spotter's `after=` cursor instead of reading one page and calling it the whole answer. The API returns a limited page (measured: 100 issuances) and says to continue from the last issuance's `id` until an empty array; an apex with more live certificates than one page lost every subdomain past the first hundred, and the coverage layer was told the answer was complete. A short page still ends the walk after one request, so a small domain costs exactly what it did out of the anonymous ten-an-hour budget. A full page is followed from its last `id`, up to five pages and only while the walk is under ten seconds old. Reaching the cap or the time budget, a later page failing, or a full page with no `id` now reports the result as truncated, and the pages already retrieved are kept. A failed first request is still the module's error. `max_timeout_ms` rises from 10 s to 25 s: the server itself allows a query 10 s before answering `504 {"code":"timeout"}`, and the old budget killed the module just before that explanation could arrive (REQ-CERTSPOTTER-001).
- The radar records the device's own Wi-Fi link on every sweep — *not connected* included — and reviews the sweep history for disruption (the second cycle of the resilience track, T6). `device_sensors` has read `termux-wifi-connectioninfo` on every sweep since the radar existed and flattened the answer into a `MacAddress` entity tagged `wifi-connected`, so a disconnection was "nothing to report": the entity graph cannot say *off the network*, and the one fact the directive turns on was never written down. Now the parser yields a typed `LinkState` beside the entities (connected, SSID, canonical BSSID, level, address, link speed, the supplicant's own state, the read time) — a blank answer is a *disconnected* record, and a real address beside a supplicant state that means "not associated" is the last network, not the current one — which travels the `ModuleResult` seam as the sightings do and is persisted by the engine's one finalise path into a new `wifi_links` table, one row per sweep, never on a cache replay. `core::link::review` — pure, no I/O, no clock — reads the history (each sweep's link record plus the Wi-Fi access points its sightings heard) for a **forced disconnection** (off the network while the access point it was on is still heard at −75 dBm or better: the link did not fade, it was cut), **deauthentication suspected** (three or more forced disconnections from one access point within an hour, the densest window), an **evil twin** (a known network name from an address never seen, louder than the known address heard in the same sweep — an unheard known address is another site, not an impostor), a **periodic outage** (more than three outage starts whose gaps all sit within 15 % of their median: outages on a schedule are a process, not weather), and the outage timeline the others sit on. Every finding carries the same advice on the page and in the shell — Protected Management Frames, cell data, forget the network — so the two cannot drift. `GET /api/v1/radar/disruptions?limit=` and `hse signal --disruptions [--json]` share ONE assembly (`app::signal::link_sweeps_from_history`) and ONE presenter; a sweep from before the record existed is counted in `unrecorded_sweeps` and left out rather than guessed. A "Network disruption" panel on the Radar view lists the findings with their advice and is refreshed on every sweep completion, on a stream's return, in the degraded poll and at load; the sweep-once path now refreshes every review built on the history, not just the rows. OBSERVED on a real `hse serve` with the five Termux tools scripted, the link shim flipped to Android's "no network" answer between two sweeps that ran within one second: on the pre-fix binary the endpoint is the api fallback's `404`, the flag an unknown argument, and the second sweep leaves no row anywhere; on the fix, a `wifi_links` row per sweep (connected, then `DISCONNECTED` with no address), the review `sweeps 2, connected 1, disconnected 1` with `forced_disconnect` (LabNet, `00:1a:2b:3c:4d:5e`, heard at −45 dBm) and its advice in the shell, as JSON and over HTTP, and the same after a restart. In Chromium the panel shows the finding with its advice after the second sweep and again after a reload. The end-to-end lock's first run found that two sweeps in one second were ordered by their random ids — at the review and in `radar_history` itself — so the history's tiebreak is now creation order (the rowid) and the review keeps the given order within a second (REQ-RESILIENCE-002).

- The console survives its own server dying and coming back (the first cycle of the resilience track, T6 in the roadmap). The live-session stream (`openLiveSse`, shared by the Live page's stream panel and the Radar view) now reports its state exactly as the scan-log stream always has — `open` / `error` with the browser's own reconnecting-or-closed distinction — and the Radar view acts on it: "reconnecting…" while the browser retries, the 8 s poller taking over meanwhile (`S.radarStreamDown`), a full re-read of signals, recurrence and the session list on `open` after a drop because a broadcast stream replays nothing emitted while the link was down, and a stream the server closed for good released so the poller can re-attach if the session is listed again. `API._req` raises one "console unreachable" banner under the header when a request gets no answer at all and lowers it on the next answer — every page shares it, none keeps its own copy; the Live page's stream panel gains a live/reconnecting/disconnected pill; a retry loop for the health read at load was tried and removed by this cycle's own matrix: the shell and the API are one process, so the scenario it waited for cannot occur. And `live_events_sse` answers `404` for a session this process does not know — the browser does not retry a non-200, so a console reconnecting after a restart learns at once that its session went with the old process instead of reading a silent pipe as live (the first run of the exercise did exactly that). OBSERVED in Chromium against a real `hse serve` killed with SIGKILL under an open Radar view mid-radar and restarted on the same port: the banner raised within one poll, the status `stream reconnecting… (polling meanwhile)`, the five rows kept; after the restart the banner lowered, the stream `closed — polling`, Start offered again, the history repainted; one tap resumed with a sweep on the new session; a page opened fresh after the restart showed the last sweep (REQ-RESILIENCE-001).

- The Radar view follows a continuous radar in real time, and recurrence is reviewed from the readings. Three things were missing after the map. The view learned of new sightings by polling "latest" every 8 s and knew only the session it had itself started; a device's track stopped at one sweep; and `radar_recurring` walked the entity graph, where its own header says signal, position and time are never stored. Now: the view opens the session's own SSE stream (`/api/v1/live/{id}/events`, the one the Live page tails) and refreshes on `scan_complete` — the engine persists the scan, then emits the event, so the readings are there when it arrives — shows the sweep number on `live_tick`, releases on `live_stop`, and recognises a running radar it did not start by the one thing only the radar sets, `allow_live_sensors` on the session's scan options, so Stop works after a reload; the timer polls only while no stream is attached (the shell's `hse radar` and an import are producers a stream cannot see). `GET /api/v1/radar/devices/{network_id}/track` returns one device's sightings across every sweep and import, oldest first, capped to the newest N, through a new `network_id` index; the view draws them as a trail on the map and a level-over-time sparkline beside the per-sweep rows. `radar_recurring` builds each sweep from `rf_devices_for_scan` — the level and the place — with the AU-117 bonded flag looked up on the sweep's entities where it lives; `RecurringDevice` carries `best_signal_dbm` and `distinct_positions` (to ~10 m); a sweep from before readings were kept is read from its entities as before and counted in `legacy_sweeps`, so the review says how much of its window is level-blind. A "Recurring across sweeps" panel — the oracle app's tracker count — lists them with a Track button. OBSERVED end to end: a two-iteration radar over the scripted sensors announces each sweep on the bus (tick, then completion, in order) with the readings readable at the moment the completion arrives; the one universally-administered fixture recurs at −80 dBm while the named `aa:…` addresses cannot; its trail runs through both sweeps. In Chromium: the status follows the stream (`sweep done at …` on the first completion, two signal reads in the whole run — none on a timer), a reload adopts the running radar with Stop still offered, the second sweep raises the recurring count to two, Track draws a two-point trail, and the first run of that exercise found a silenced consumer error, which is why the stream's catch now drops only unparseable frames (REQ-RADAR-004).

- The Radar view has a map. The console's CSP is `img-src 'self' data:` and stays that way, so the browser cannot load a tile server's tiles itself — and should not: a tile server would learn where the operator is looking from a referer it never chose to send. `hse serve` now proxies tiles through `GET /api/v1/tiles/{z}/{x}/{y}.png` with an on-disk cache under `~/.huntsman/tiles`: cache first (a map seen once is there offline, kill-switch or no upstream), else one guarded fetch with the crate's own User-Agent — what the OpenStreetMap tile policy asks of an application — streamed to a hard cap and refused unless it is an image, then cached atomically under owner-only directories; an out-of-range tile is a `400` that never reaches the upstream, an upstream failure a `502` naming the upstream host and caching nothing. The upstream is `HUNTSMAN_TILE_UPSTREAM` (any `{z}/{x}/{y}` server; the policy forbids heavy use of OSM's own servers by a distributed application, so it is one variable away) and `feature.map_tiles` is a kill-switch for the outbound fetch only. The view draws a dependency-free Web-Mercator map (`js/radar_map.js`, ~150 lines, tiles reused across pans, attribution the policy requires) with every positioned device at its position — a live sweep's readings share the sweep's fix and cluster on one marker with a count; a wardriving import spreads out — and nothing placed where it was not heard: a sweep with no fresh fix shows no map and says why. OBSERVED against a stand-in upstream: the first tile `x-hse-tile: upstream` and a `0600` file, the second `cache` with the upstream hit count unchanged, out-of-range `400`, the switch off refusing an uncached tile while the cached one still serves, the upstream killed and the cached tile still serving, a restart serving it again; and in Chromium, six tiles decoded from the proxy, a five-device cluster at the fix, the marker moving with a pan (REQ-RADAR-003).

Every reader of `rf_sightings` was an inherent method on the SQLite `Store`, not on `StoragePort`, so no HTTP handler — which sees only `Arc<dyn StoragePort>` — could read a single row: OBSERVED on `78a4b643`, `GET /api/v1/radar/signals` answered the api fallback's `endpoint not found`, and the SPA's only radar surface was an activation button and a sweep list on the Live page whose "Review" link opened the entity graph, where the reading has already been dissolved. - A live radar sweep now records every reading as an RF sighting. `core::rf::RfSighting` and the `rf_sightings` table — position, level and time per reading, with a geo index and every analytic over it (`hse signal`, `rf_devices_for_scan`, trackable devices, the summary) — were written by the file importers only; `signal_radar` returned entities, which flatten the reading away (`core::rf` says so in its own header), and `RfSource::{WifiRadar, BluetoothRadar}` were declared for exactly this path and constructed only in tests. `hse signal`'s own hint, "or run a radar sweep first", promised what a sweep never delivered. OBSERVED through the real binary with the four Termux tools scripted: the same sweep (5 sensor modules, 13 entities) reads `sightings: 0` on the pre-fix binary and `sightings: 5, devices: 5, wifi: 2, ble: 1, bt: 1, cellular: 1, with_position: 5, named: 3` on the fix. `ModuleResult` gains a typed `sightings` channel (the `truncation` precedent); the Wi-Fi, Bluetooth and cell parsers push one sighting per reading (`le` → BLE, everything the classic-discovery shim reports otherwise → classic with the tool's type kept verbatim; a new `RfSource::CellRadar`); the sweep's own GNSS fix is stamped onto every sighting that has no position of its own — never over one that does, and only from a fresh lock: a `last`-known read still yields the `Coordinates` entity tagged `fix-age:last-known` but positions no sighting, because a cached position is not where the devices were heard from now — and the engine persists them in the one finalise path every dispatch mode shares, best-effort like the entity checkpoint. Locked at the parsers, the stamping rule (with its over-correction control), the engine seam (with a cache-replay control) and end to end through the real router with scripted tools, reachable without `unsafe` through `util::termux::tool_dir_for_tests`, the `paths::isolate_for_tests` pattern (REQ-RADAR-001).

- A scan killed without a cooperative shutdown no longer reads as `running` forever. `cli::serve` drains in-flight scans on Ctrl-C/SIGTERM so each reaches a terminal state, but that is the cooperative path only; on SIGKILL, OOM, or Android reclaiming a backgrounded process — which `storage::entities` itself calls "routine on Termux" — the row was left at `running` with no process to finish it, and nothing reconciled it at startup. Not argued from source: OBSERVED on `ff4d63c` by putting a scan genuinely in flight (two modules, fully sequential, a 30 s inter-dispatch throttle so the kill lands inside the sleep with no network), `kill -9`, restart — the row still read `running`, `/stats` answered `{'running': 1}`, `GET /scans/{id}` showed `finished_at: null`. The two scans left by the earlier graceful SIGTERM in the same database read `complete`, so the defect is confined to the non-cooperative exit. The data was never lost — `entities_from_events` already recovers it — only the reported state was wrong (REQ-SCANSTATUS-001).

- The registry that derivation reads is now the ONE every spawn path fills. The first draft read `AppState.cancellations`, which only `spawn_scan` populates; the live loop ran the engine itself with a per-iteration handle registered nowhere, so — OBSERVED through the real router on that draft — a healthy live iteration read `interrupted: true`, `/stats` counted it, `DELETE /scans/{id}` mid-run returned 200 (the exact race `scan_delete`'s own comment documents, open for every live iteration all along) and `POST /scans/{id}/cancel` returned 404 while this very process was running it. `CancelRegistry`/`CancelRegistryGuard` move into `core::cancel`, `LiveScanner` takes the registry, and each iteration registers under its scan id with its own handle for exactly as long as the engine runs it; every `AppState` shares its instance with its `LiveScanner`. A live iteration is now cancellable by scan id (that iteration only — the session continues), refused deletion mid-run, counted by the shutdown drain, and never reported interrupted by the process running it. Locked at the live loop's boundary and through the real routes with a gated test module that holds a scan genuinely in flight (REQ-SCANSTATUS-001).

- The fix derives and never mutates. A `running` row that THIS process holds no cancellation handle for is reported `interrupted: true` on `GET /scans` and `GET /scans/{id}` (both through one `scan_json` authority, so they cannot disagree) and histogrammed under `interrupted` by `/stats`; the persisted row is left exactly as the dead process left it. The one-line alternative — rewrite every `running` row to `failed` at startup — was rejected because a second instance sharing the database would have its live scan marked failed underneath it, relocating the defect rather than removing it. The design rests on one assumption, verified in `spawn_scan` rather than assumed: the registry guard is the spawned task's first binding and drops last, after the engine's final status write, so within one process `running` with no handle is impossible and only a dead process produces it. `Pending` is deliberately excluded — it has a legitimate no-handle window between `upsert_scan` and `spawn_scan` — and that exclusion is asserted by a control, not left incidental (REQ-SCANSTATUS-001).

- PR #637's own recorded follow-up is closed with evidence instead of left standing. REQ-EXPORT-001 fixed five export seams and noted that "the sibling sweep should re-check any other place entity evidence is serialized"; nobody had. That last row was the one worth chasing, because a bare sink is only as good as every producer above it — so every module-built error interpolating a url or endpoint was read: `ripestat`/`niamonx` interpolate a path segment, `sitemap` the SUBJECT's own crawled URL (a finding, which must survive), `stolen_tax` builds its URL into a local and never into an error. No module bypasses the upstream redactor (REQ-EXPORT-002).

- The gap the audit found was a missing lock, not a leak. The debug bundle is exercised by six tests, none about secrets, and it deliberately opts OUT of the default-safe provider-name redaction — which makes it easy to read as opting out of redaction altogether. Its safety rested entirely on a delegation nothing asserted. `debug_bundle_masks_an_operator_key_echoed_in_evidence` now asserts it, with the subject finding surviving verbatim as the control, because the bundle's "nothing hidden" contract is its reason to exist and a lock satisfied by redacting evidence wholesale would destroy that while passing. A test at an inner boundary does not cover the artifact that composes it, and the composition is what ships to the reader. No sink-side redactor was added to `render_event_log` — nothing feeds it an unredacted secret today, so a second pass there would be a speculative abstraction; the ledger records where the guarantee actually lives instead (REQ-EXPORT-002).

Recorded as hardening against a structurally possible input, not as a live bug; the control pins that a real 32-hex MD5 — the narrowest recognised width, closest to the old floor — still mints and still classifies (REQ-OATHNET-002).

- A half-configured `censys` no longer asserts that censys holds nothing on the subject. It authenticates with HTTP Basic `api_id:api_secret` — its own header says both are required and `process` sends them together — but only the ID arm returned `Error::MissingKey` for an absent credential; the secret arm, **two lines below it**, returned `Ok(ModuleResult::new())`. Dispatch records an empty result as `ModuleDone { found: 0 }`, which coverage aggregates to `ProviderOutcome::CleanNegative`, documented as "the only outcome that is a real negative" and the one `settles_absence` trusts. So a missing secret was reported as a clean negative for a provider that was never contacted. This is the contract REQ-KEYSKIP-001 established and applied to ~8 modules, including the ID arm immediately above. A sweep of every credential lookup in `src/modules` with a quiet-empty miss arm found this the only survivor tree-wide: `dehashed` and `fofa` propagate via `ctx.key(KEY_ENV)?`, and `github_user` is documented keyless, so its empty return is a genuine missing profile. Reproduced on the unchanged module before the fix, and the control pins that with *neither* credential the ID is still the one named (REQ-KEYSKIP-002).

- `niamonx` no longer reports a call the provider said failed as a clean miss. Its three endpoints each return `Result`, and `process` already turns an `Err` into `hard_failure` / `or_hard_failure` and drives the key-rotation cascade when all three fail — but `success: false` never reached any of it, because the check lived one layer later in emitters that return `()` and therefore cannot report a failure even in principle. Reproduced on the unchanged module: `success:false` yields zero entities, zero evidence, and `Ok`. The task was parked as "live success:false shape not confirmed"; that asked the wrong question, since what matters is what the flag MEANS, and four in-repo signals settle it — the `data.status == "not_found"` branch the code itself calls "the documented no-results response" sits *after* `if !resp.success` and would be unreachable if a miss arrived that way; all three fetches say "empty results arrive as 200+body"; `breaches_s_v2` carries a separate inner `data.niamonx_success`; and the module's own miss fixture is written `success: true`, with no fixture anywhere in the file setting it false. Three structurally identical response types collapsed into one generic `Envelope<T>`, sealed with the single function that may open it in a private submodule: outside it the flag cannot be read, the payload cannot be taken, and an envelope cannot be constructed, so the only route from a body to a payload is the check. Six silent returns and three near-duplicate structs are gone. The over-correction control needed no new code — every fixture now reaches its emitter through `payload(…).expect(…)`, so a repair that errored on honest misses would panic the pre-existing `not_found` / `stats.total == 0` / `niamonx_success:false` tests instead of passing quietly (REQ-NIAMONX-001).

- `fofa` no longer reports an upstream failure as "no indexed infrastructure for this host". `FofaResp::error` was a bare `bool` under the struct's `#[serde(default)]`, and the envelope check opened `if !body.error`, so a 200 body that is valid JSON but not a FOFA envelope — `{}`, `{"message":…}`, an `{"errmsg":…}` without the flag — decoded to `error: false, results: []` and was handled as a successful search with zero results. Default `false` means "no error": the module failed OPEN, which is the one sentence its own envelope comment forbids and the `ProviderOutcome` doctrine's central prohibition. No live access was needed to establish it — the contradiction is inside the file — and it was reproduced on the unchanged module first. The obvious repair, `error: Option<bool>` failing closed on absence, is **rejected**: `chain_intel` and `au_geo` can do that because their sentinel is a field a real response demonstrably echoes, while this module's header documents no response shape at all, so refusing on a missing `error` would trade a fail-open for a fail-shut and break every real search if the flag is omitted on success. Both `error` and `results` are now `Option` and only a body carrying **neither** is refused — the weakest condition that still rejects `{}`; the assumption that a search response carries at least one of them is recorded as an assumption. The two booleans read in sequence became one exhaustively-matched `BodyVerdict`, since the third outcome previously had no representation and silently wore the first one's clothes. The key cascade is locked too — a credit-exhaustion envelope must actually retire the key, while `errmsg: "query syntax error"` must leave it alone — after an earlier claim in this cycle that such a test would write to the operator's real `~/.huntsman/key_pool.json` turned out to be wrong: `paths::huntsman_dir_path()` redirects to a pid-scoped temp home under `cfg!(test)`, which four links of that chain were read without reaching (REQ-FOFA-001).

- The rule REQ-OPENMETEO-001 left behind is corrected by applying it. Swept as a population, not a sample: every struct in `src/` and `hse-core/src/` with a container-level `#[serde(default)]` over a bare non-`Option` field — nine, each then read at its use sites. **Seven are correct by design**, so the rule as written fires nine times and is right twice, which is a rule the next reader learns to ignore. It now reads: safe iff **either** a container-level sentinel distinguishes "no response" from "a response of zeros", **or** every use site guards the default; a defect only when neither holds. `chain_intel` was this cycle's first candidate on the strength of the grep — six bare numeric balance fields, where a fabricated zero is a financial claim — and reading it refuted that ranking outright: a dormant address returns a real object full of zeros, so a zero inside is genuine and per-leaf `Option` would be actively wrong. It is the exemplar, not the defect. The nine-site table is in the ledger (REQ-FOFA-001).

- Corroboration that arrives for a discovered target *during its own dispatch round* now re-opens the gate it was short of. `target_distinct_sources` is computed once before the module loop and every gate in that round reads the frozen value, so a target that crossed `CROSS_CORRELATION_MIN_SOURCES` mid-round never re-triggered the check — and because a target is visited exactly once (`visited` in `engine::mod`), the skip was **permanent**, not deferred to a later round: a paid, high-value-only module that had become eligible simply never ran. The premise the earlier measurement left open — whether the count actually grows during a target's own round — is now verified: on the unchanged engine the discovered Username ends with exactly 2 corroborating sources, asserted as a premise guard *before* the gate assertion, so the lock's baseline red is provably at the gate rather than at a count that never moved. A **round barrier** re-dispatches gate-deferred modules once per round through the same sequential loop, which recomputes the count at its top and re-runs every gate; the deferral list is sorted by module name first, because the two concurrent phases append in completion order and the earlier measurement rejected a naive per-module recompute for exactly that nondeterminism. Whether a skip is deferrable is decided by re-running the gate at a saturated count, not by matching its reason string or keeping a second list of source-count rules that could drift from the rules. The barrier pass records nothing — a re-evaluation is not a second dispatch attempt — so one gated module still books one skip and emits one `ModuleSkipped`. The control matters more than the lock: a repair that fired a paid module on a single-source entity would be strictly worse than the conservative defect, and it was landed green before the change (REQ-ENGINE-002).

- The control-probe cache is now scoped to the scan, completing REQ-PROBE-005. A successful control answer lived in a process-lifetime `static` keyed on the control URL alone, so an answer read during one scan decided every later scan in the same process — correct inside a scan, stale across them, and under `hse serve` that process runs indefinitely. The key is now `(scan, url)`, taking the scan from the ambient the engine already establishes around every scan and re-applies inside each spawned module dispatch. The ledger's own earlier note predicted this "needs a scan-scoped container threaded through" two callers and was "a design question rather than a one-line correction"; that was wrong twice — `budget::current_scan()` already existed and its doc names "the provider response caches" as its intended consumer, and there are three callers, not two. Nothing was threaded and no caller changed. The over-correction guard matters as much as the fix: a mutation that simply stops caching is killed by the new lock's non-vacuity half and two pre-existing tests (REQ-PROBE-005).

- `open_meteo_geo` no longer places a hit on the equator because the provider omitted its latitude. `GeoResult` carried a struct-wide `#[serde(default)]` over two **bare** `f64` coordinates — the attribute is there for the enrichment fields, every one of which is already `Option` — so a response omitting `latitude` deserialized to `0.0` instead of failing, and `0.0` beside a real longitude passes `is_valid_coords` *correctly*, because the equator is a real place. A hit with no latitude produced `0.000000,151.209300`: a real Sydney longitude welded to a fabricated latitude. Both components are now `Option<f64>` and a hit missing either is skipped, matching every sibling geo module; the skip costs no `RESULT_LIMIT` budget, as an invalid-coordinate row does not. The lock that matters is the one asserting an **explicit** `"latitude":0.0` is still KEPT — the obvious fix, "drop any row with a zero component", would have re-introduced inside this module exactly the cross-shaped rejection REQ-GEOGATE-001 removed from the coarse-provider gate (REQ-OPENMETEO-001).

- The verification gate no longer exhausts its own disk, and a full volume no longer masquerades as a compiler bug. `scripts/gate.sh` set `CARGO_INCREMENTAL` nowhere — nor does any workflow or `.cargo/config.toml` — and incremental state is never reclaimed, so it accumulated until the volume filled: one from-scratch run took `target/debug/incremental` from `4.0K` to **7.6 GiB**, and a run died mid-`test` at 98% full with `LLVM ERROR: IO failure on output stream: No space left on device` surfacing as `ld terminated with signal 7 [Bus error]` and `could not compile (lib test)` — which reads as a defect in whatever change is under test, and was taken for one. The script's own header says a gate that quietly drops a check is worse than no gate "because it reports success it did not establish"; reporting a *failure* it did not establish is that same defect inverted. `CARGO_INCREMENTAL=0` is now exported — convergence with CI, which has always run with incremental disabled because every workflow here uses `Swatinem/rust-cache`, and that action sets the variable itself and keeps incremental artifacts out of its cache; `gate.sh` was the only place in the repository that did not. A preflight refuses to start below a free-space floor with a message naming the disk and the reclaimable paths, and `run()` re-measures on any failed check against a separate near-exhaustion line to flag a probable disk cause without crying wolf on genuine failures. A single `cargo check --lib` produces 297 MiB of incremental state without the export and 4.0K with it (REQ-GATE-001).

- The coarse-provider coordinate gate rejected a **cross**, not a square, and thirteen modules went blind along the equator and the prime meridian. `is_plausible_provider_coord` exists to drop the near-null-island placeholder those APIs emit when they have no fix — a point near `0,0` — but it was written as `lat.abs() > BAND && lon.abs() > BAND`: accept only if *both* components clear the band, i.e. reject if *either* does. That is two ≈2.2 km-wide strips running the full length of the equator and the full length of the prime meridian, so `censys`, `criminal_ip`, `geo_intel`, `ip_geo`, `ip_whois_geo`, `netlas`, `wifi_intel`, `wigle`, `ip2location`, `ipinfo`, `ipquery`, `onyphe` and `zoomeye` could not report a fix at the Royal Observatory, in Pontianak, in the Gironde, in Nanyuki or on the Ghanaian coast. The codebase contradicted itself about the same point: `is_valid_coords`'s doctest called `(0.0, 153.0)` *"a real equatorial fix"* while two other tests asserted it was a placeholder — and two of the three assertions pinning the wrong shape used coordinates that are real inhabited places — Central Sulawesi and the Gironde — as their examples of what must be discarded. The gate now rejects the Null Island **square**; every placeholder sample any provider here has been observed emitting (`0.001,0.001`, `0.005,0.005`, `0.004,0.004`, `0.005,-0.002`) puts both components inside it and stays rejected, as does the band edge (REQ-GEOGATE-001).

- `wigle::emit::emit_bssid_entities` no longer fabricates a longitude of zero. It bailed on a missing `trilat` and then wrote `unwrap_or(0.0)` for `trilong` one line later; the old cross-shaped gate hid it, because a fabricated `0.0` longitude always fell in the rejected strip. Correcting the gate would have turned `51.4779, 0.0` into a first-class `geoint` fix on the prime meridian for a network WiGLE never gave a longitude for, so the root cause is fixed in the same commit — a missing component is not zero (REQ-GEOGATE-001).

- REQ-WIGLE-001's jitter-band fix is regression-locked at all three of its call sites instead of one. Downgrading either of the two unguarded emitters to the weak `is_valid_coords` left all 52 of `wigle`'s tests green, so the fix could have been reverted at two thirds of its surface without anything noticing; both emitters are pure, and the new locks assert on the returned entity list with a non-vacuity half so they cannot pass by emitting nothing. `NULL_ISLAND_BAND`'s **width** is now pinned too — widening it a hundredfold previously killed no test at all (REQ-GEOGATE-001).

- The architecture enforcer that exists so "a new (or edited) coarse provider can't silently pick the wrong validator" is now a registry instead of a sample. Its `COARSE_PROVIDERS` list carried the same six names the `is_valid_coords` doc did, against thirteen real call sites, and it only ever checked one direction — "every module I name gates its coordinates", never the converse — so seven modules could be downgraded to the weak `is_valid_coords` with it green. Both directions now run, the satisfying pattern is the CALL form rather than a bare substring a leftover `use` import could satisfy, and a vacuity guard requires the file walk to have found every declared provider (REQ-GEOGATE-001).

- The five providers the gate review was filed against — `wifidb`, `mylnikov`, `beacondb`, `cell_intel`, `cell_local` — stay on `is_valid_coords`, and the premise that they are "the same family as WiGLE" is **refuted** for each. Every one signals "no fix" out of band: a `fallback` marker carrying the caller's own IP position (`beacondb`), an in-body `result:404` handled before the gate is reached (`mylnikov`), an empty `FeatureCollection` (`wifidb`), a `status:"error"` (`cell_intel`), an offline database read that is not a provider response at all (`cell_local`). WiGLE is the outlier, not the archetype: its no-fix rides in the coordinate field itself, which is the only reason the band gate exists. The selection rule now lives in `is_valid_coords`'s doc as a rule rather than the list of module names it used to carry, which had drifted to naming six of the thirteen actual call sites (REQ-GEOGATE-001).

- The last two private truncation vocabularies are migrated onto the shared completeness mechanism, completing REQ-COVERAGE-001's consolidation. `web_crawler`'s `image_leads_capped` and `netlas`'s `result_count` both already knew the true total and the emitted count — and both kept that knowledge in an evidence attribute with **no reader outside its own file**, which is the defect REQ-COVERAGE-001 identified in five modules and fixed in three. Each now also declares it at the provider level through `ModuleResult::mark_truncated`, taking the known-total arm (`"20 of 213"`, not an unknown), so a capped crawl and a capped Netlas query reach `ProviderOutcome::Truncated` and the readers that already exist. The per-entity attributes stay as dossier detail (REQ-WEBCRAWLER-003, REQ-NETLAS-001).

- A region label no longer earns the centroid of the city inside it. `city_coords` matches a tabulated name as a consecutive run of whole tokens, so `"New York State"` — tokens `["new","york","state"]` — contained the run `new york` and resolved to **Manhattan**: a precise-looking fix on the one place the string exists to exclude. Same for `"Upstate New York"` and `"Greater London"`. This is `place_grain::is_bare_country`'s defect one grain down — that predicate exists because forward-geocoding a bare country name returns a centroid that "is never a subject's location" — so the new `negates_city_grain` sits beside it. Deliberately narrow, because the expensive failure here is losing a real fix: `"New York"`, `"New York, NY"` and `"12 Smith St, Perth, Australia"` all still resolve, and the qualifier must be a whole leading or trailing token so `"Statenville"` is untouched (REQ-SOCIALLOC-002).

- `see_know`'s identity-pivot walk now says whether it finished. Its own doc lists four exits — *"no new IDs appear, a hop yields no new entities, the per-scan budget is spent, or `MAX_PIVOT_HOPS` is reached"* — and only the first two mean the chain was fully walked. The other two, plus a mid-hop budget guard that silently skips a non-empty dispatch, mean the chain was still producing when something unrelated to the subject stopped it. All of them returned an indistinguishable result, so a pivot chain cut short by a spent quota looked exactly like one that ran to the end. The walk now records which exit it took and, for the three incomplete ones, declares it through `ModuleResult::mark_truncated` — reaching `ProviderOutcome::Truncated` and the readers that already exist. Each cause reads differently, because a quota an operator can raise and a structural hop ceiling they cannot are different facts (REQ-SEEKNOW-001).

- `parse_pdf` enforces a size ceiling, and stops allocating a second copy of every file it reads. It called `fs::read` with no limit, then `String::from_utf8_lossy` over the result — which for a PDF (binary, mostly not valid UTF-8) allocates a whole second copy, and a **larger** one, since each invalid byte becomes a three-byte U+FFFD. Peak cost was a multiple of the file, on input arriving from outside, and all of it to count two ASCII needles for a heuristic page count. The markers are now counted on the bytes (proven equivalent: both needles are ASCII, lossy conversion leaves valid ASCII untouched, and U+FFFD cannot manufacture a match), and the new `MAX_DOCUMENT_BYTES` ceiling is checked from the **directory entry before the read** — a cap applied afterwards would have already made the allocation it exists to prevent. `DocumentParseError::FileTooLarge` had been declared, carried a `{0} MiB` message, and was **never constructed anywhere in the tree**; it now has exactly one constructor (REQ-DOCPARSE-002).

- A control probe that **failed** is no longer remembered as the site's answer. `util::probe::control_presences` caches one control answer per URL so a multi-target scan asks each site once — and it cached `ProbeResult::Error` alongside the real answers. `controlled()` turns a presence judged against an errored control into `Uncontrolled`, or into `Found { controlled: false }` (whose own doc reads *"False when the control could not be read"*), so a single transient network failure marked **every future presence on that site uncontrolled for the life of the process** — under `hse serve`, indefinitely. Failures are now skipped and the site is simply re-asked; successful answers are still cached, which two over-correction mutations confirm (caching nothing, or also dropping `NotFound`, breaks the existing cache test). This is the doctrine `core::coverage::ProviderOutcome` states one layer up — PROVIDER FAILURE ≠ ZERO EVIDENCE — applied to the cache that decides whether a presence can be confirmed (REQ-PROBE-005).

- `module_skip_reason` no longer reads the process-global circuit breaker inline. Every other input to that gate was an argument; the circuit verdict was not, and it lives in a `Mutex<HashMap<&str, Trip>>` keyed by module NAME — so any test that trips a circuit (`record_rate_limit`, `record_soft_failure`, `record_bot_challenge`) changed what every *other* test asking about that module saw, in whichever order the harness happened to run them. Two `skip_reason` tests passed only under `--test-threads=1` for exactly that reason. The verdict is now injected through `module_skip_reason_with`, the public entry point still consults the real circuit (unchanged in production — a mutation that stops it doing so fails `circuit_breaker_trip_skips_the_module_at_the_dispatch_gate`), and the ~40 gate assertions state `circuit_open: false` as a fact instead of hoping for it (REQ-CI-004).

- The config-leak sweep's port invariant is now asserted on a string instead of on a race. `web_crawler`'s `host_root` construction moved out of the network-bound `probe_config_leaks` into a pure `host_root_for`, and the socket test that used to require **all** `CONFIG_LEAK_PATHS` probes to arrive now asserts only that the seed's ephemeral port was reached. The old assertion made a property of the URL builder depend on 103 concurrent requests all completing inside one 3-second client timeout: a probe abandoned while still in the listen backlog is never accepted, so a loaded runner subtracted from the count and failed the build with the code correct — twice in CI, once as `left: 98 right: 100`, and a previous fix that moved each connection onto its own task did not hold. Relaxing the count is safe **only** because the deterministic lock now exists: what the test catches — probes aimed at the scheme's default port rather than the seed's — yields zero hits, never a near-miss, which the falsification confirms by dropping the port and watching all three locks fail together (REQ-CI-010).

- `mnemonic_pdns` de-duplicates passive-DNS records **by relationship, not by bare value**. Its key namespaced IPs against hostnames — *"IPs under an `ip:` key so a host and an IP string never collide"*, as its own doc put it — and let everything else share one key space, with two silent consequences. A host serving as both the target's **MX and its NS** kept only whichever record the API listed first, losing a tag and an entire observation window; and a host that both receives the target's MX **and CNAMEs into it** lost one of two opposite DNS facts. Keys are now `rev:{query}` / `ip:{canonical}` / `fwd:{rrtype}:{host}` / `in:{query}`: the rrtype and the direction are part of the assertion, not decoration on it. What still collapses is the same assertion repeated — two MX records naming one host remain one relationship however often the API repeats them, including across trailing-dot and upper-case spellings (REQ-MNEMONIC-001).

- `zoomeye`'s client-side `.take(MAX_MATCHES)` cap is no longer silent: a host whose service surface fills all 50 matches now declares the sweep bounded. `ZoomResp` models only `matches` — deliberately, so an error envelope fails closed (REQ-ZOOMEYE-001) — and the provider's own hit count is not among them, so the **full page** is the signal and the total is reported as unknown rather than guessing a wire field name that could silently never populate (REQ-ZOOMEYE-002).
- `ModuleResult::mark_truncated_if_capped(returned, cap, cause)` — one authority for the commonest truncation shape, a page returned full against a known ceiling with no provider total available. `mnemonic_pdns` and `zoomeye` both use it; the short-page guard that keeps an exhaustive answer from being flagged now lives in exactly one place instead of being re-derived per module. Written after the second module needed it, which is where REQ-COVERAGE-001's five private spellings started (REQ-ZOOMEYE-002).

- `mnemonic_pdns` now keeps the completeness promise its own header makes. The module's doc states, under the Operational Constitution, that this API returns *"a sample — the most-relevant `RESULT_LIMIT` records, not the exhaustive set"* — and that promise was kept per-entity (first/last-seen, observation count) and nowhere the coverage layer could read it. A domain capped at 100 records and a domain with exactly 100 records to its name produced identical coverage, so absence of a passive-DNS edge read as evidence of absence either way. It now declares the bound through `ModuleResult::mark_truncated`, reaching `ProviderOutcome::Truncated`. The signal is deliberately the page being **full**, not the `count`/`metaData` siblings this envelope ignores: their semantics (records in this page? matches overall?) are established nowhere in this repository, and a confidently wrong total is worse than an honest unknown — so the unknown-total arm is used, which says in as many words that the provider did not report how many exist. The decision moved out of the network-bound `process` into a pure `page_was_capped` seam, and a **short page is asserted never to be marked truncated** (REQ-MNEMONIC-002).

### Fixed

- Both operator-facing sentences produced by `ModuleResult::mark_truncated` carried a run of literal spaces — *"did not report how&nbsp;&nbsp;&nbsp;…&nbsp;&nbsp;&nbsp;many exist"*. They were written with `\`-continuations across source lines and `cargo fmt` rejoined them, leaving the indentation in as text. These strings ship straight to an operator via `report.json`, the dossier appendix and `/api/v1/scans/{id}/coverage`, and nothing would have caught it: the sentence still contained every word a `contains` check might look for, and a whitespace run is invisible in a diff of a long line. Guarded on the **shape** of the rendered sentence rather than its wording (REQ-MNEMONIC-002).

### Added

- **`core::coverage` can now say a provider answered INCOMPLETELY.** `ProviderOutcome` gained a fifth state, `Truncated { reason }`, alongside `Observed` / `CleanNegative` / `NotAttempted` / `Failed`. A provider that returned the first 20 of 213 matches used to report `Observed` — byte-identical to one that returned everything — in the very enum whose doc warns that "collapsing the three is the commonest way a system invents a confident clean answer about a hard target". The absence of that state had forced five modules to each invent a private evidence-attribute vocabulary for it (`sitemap_enumeration_truncated`, `historical_subdomains_truncated`, `web_crawler`'s `image_leads_capped`, `netlas`'s bare `result_count`, `domainsdb` spending its parsed `total` on one `> 200` boolean), and **not one of those keys had a single reader outside its own file** — nothing downstream could ask whether a result set was complete, because every module spelled the question differently. Modules now declare it once via `ModuleResult::mark_truncated(emitted, total, cause)`, which reaches coverage through a new `#[serde(default)]` field on `EventKind::ModuleDone` (old persisted events still decode, reading as "nothing claimed"). The distinction between a known and an unknown provider total is kept rather than flattened to `truncated: bool`, because "20 of 213" and "20, and the provider did not say how many exist" call for different operator actions. Wired for `domainsdb` (which already parsed the total), `sitemap` and `wayback`; the existing per-entity attributes stay as dossier detail. Read for free by the CLI dossier appendix, `hse report --benchmark`, `/api/v1/scans/{id}/coverage` and `report.json`, whose wire spelling is the distinct `"truncated"` (REQ-COVERAGE-001).
- **A truncated provider's silence can no longer close a claim.** The new state exposed a second judgement hiding behind one predicate: `ProviderOutcome::is_resolved` was answering both "did this provider run?" (which gates `skip_class`) and "can its silence be trusted?" (which gates `core::intelligence`'s `coverage_gaps`, and through it `reject_claim`). A truncated provider answers **yes** to the first — it ran, and filing it as unavailable would misdescribe a provider that worked — and **no** to the second, because it searched part of its corpus and the evidence may be in the part it never retrieved. Split into `is_resolved` (unchanged meaning, now including `Truncated`) and a new `settles_absence`; `coverage_gaps` reads the latter, so a claim can no longer be rejected on the strength of a page nobody read. Both halves locked, including a mutation that collapses them back together.

- `xposed_or_not_domain` — a new keyless breach-exposure module answering "was this domain's own operator itself the victim of a known data breach", the Domain-kind analog of what `ransomware_live`/`ransomlook` already do for ransomware victims. The existing `xposed_or_not` module only asks whether an EMAIL has been exposed (`accepts` explicitly rejects `TargetKind::Domain`), so a Domain-kind seed never reached XposedOrNot's second, independent public endpoint (`GET /v1/breaches?domain=`) before this. Contract verified live against real responses (2026-09): a hit is `{"status":"success","exposedBreaches":[{breachID, breachedDate, domain, industry, passwordRisk, verified, exposedData, exposedRecords, exposureDescription, referenceURL}]}`; a clean miss is `{"status":"Not Found","exposedBreaches":null}`, also HTTP 200. An empty or missing `domain` parameter does not error — it silently returns the provider's entire breach catalogue (confirmed live), so every returned record is gated on its own `domain` field matching the queried domain (`util::domains::is_or_subdomain_of`, checked in both directions, the same authority `ransomware_live` uses) before it can become an entity — defense in depth against ever surfacing an unrelated company's breach as the target's own. Confidence is lifted when the provider's own `verified` flag is set. Surfaces breaches as recent as August 2026 (e.g. Baxter International, Manchester Airports Group), another independent corpus the `AU-001` multi-source correlation rule can draw on for a Domain seed.

- `social_location` does **not** geocode state- or country-grain text as a city point — probed directly, `city_coords` resolves no AU state, no US state and no country name, and `social_location` already tags `au-state:`/`country:AU` for state-grain text while earning no coordinate for it. The systematic claim is refuted. A narrow residual is real and re-scoped rather than fixed: `"New York State"` and `"Upstate New York"` both return New York City (~200 km off), because the whole-token matcher treats a qualifier that negates the city reading as just another token. It bites on the one tabulated name that is also a state name, and the correction belongs in `city_coords` — the shared authority every caller uses — not in `social_location` (REQ-SOCIALLOC-002).

- `wayback`'s every-run sweep timeout is **not** its query shape. Measured twice and attacked; the `collapse=urlkey` hypothesis did not survive contact with the evidence, and no change was made on the strength of it (REQ-ARCHIVE-001).
- A dispatch-gate skip on a *discovered* target is permanent — the target is never reconsidered when later evidence would admit it. Confirmed from source and measured; the remedy is a live design question (re-queue policy, expansion-floor interaction) rather than a defect with an obvious fix, so it is recorded and left unchanged (REQ-ENGINE-002).

## Rationale

Per Rule 0.7 (Decision Hierarchy), all changes prioritize:

1. **Correctness** — code must work (all tests pass, gate passing)
2. **Evidence Integrity** — data must be valid (no silent failures, explicit error attribution, honest consensus validation)
3. **Safety** — no undefined behavior (`#![forbid(unsafe_code)]`)
4. **Determinism** — reproducible results (no flaky tests, no ordering leaks)
5. **Reproducibility** — repeatable across runs (deterministic sorts, tie-breaks, no HashMap iteration leaks)

Later priorities (6-10: simplicity, performance, maintainability, portability, convenience) are deferred until P0-P2 defects are closed.
