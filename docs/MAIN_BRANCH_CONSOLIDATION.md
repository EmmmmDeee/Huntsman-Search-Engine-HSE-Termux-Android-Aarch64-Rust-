# Canonical main-branch consolidation

## Authority

`main` is Huntsman's sole canonical Rust/Android Termux implementation. Historical
branches are **candidate source material**, not parallel release lines. No older
branch is merged wholesale merely because it has unique Git commits.

A branch being thousands of commits behind `main` means its old source tree
must not replace the current architecture, even if it contains useful logic.

## Reconciliation evidence

The read-only workflow `.github/workflows/main-branch-reconciliation.yml`
fetches all remote branch refs and uploads a TSV inventory generated by the
standalone Rust tool `tools/branch_reconciliation.rs`.

Each row records:
- The exact canonical `main` SHA used as the baseline;
- The remote branch ref, exact tip SHA and Git commit timestamp;
- Commits unique to the branch and commits present on main but absent from it;
- One of `same_tip`, `already_ancestor`, `ahead_only_review` or
  `diverged_review`.

The job summary also surfaces the 20 most recently committed divergent or
ahead-only branch tips, sorting equal timestamps by how far behind `main` they
are. This is a **review queue**, never a missing-functionality score or permission
to merge. Always examine current canonical equivalents and source history first.

This is a **Git ancestry inventory**, not proof of distinct capabilities:
squash merges, partial ports and independent rewrites can make a divergent
branch semantically redundant. Conversely, an ancestral branch may still
document features not connected to the runtime. No automatic merge or branch
deletion follows from the inventory.

The workflow is read-only, uses pinned Actions and a pinned runner, keeps
`contents: read`, and runs on manually requested and weekly schedules.

## Dependency-led assimilation

For each non-ancestral branch, in order:

1. Establish its exact last commit, affected files, source data contract, and
   feature behavior against the **current** canonical modules and tests.
2. Determine whether the behavior is already present on `main` (including
   reimplementations). Mark such branches as superseded; do not re-port them.
3. Where a genuinely missing capability survives, port only its necessary Rust
   logic into existing canonical ownership boundaries. Avoid reviving legacy
   architecture, secret-bearing files or obsolete dependencies.
4. Supply failure reproductions and regression tests for the new integration
   and its historical behavior. Preserve evidence provenance and compatibility.
5. Open a focused `main`-targeted PR, keep its exact-head gates green, and
   verify Android AArch64 cross-build, Rust 1.87/1.99, ARM64 QEMU, Web UI,
   container and security gates before merging.
6. Require physical Termux runtime evidence before asserting **on-device**
   operation or performance. CI, emulation and native ARM64 Linux are separate
   assurance levels.
7. Merge an eligible PR with an expected-head guard, then verify the **new main
   merge SHA** independently. Record its relationship to the source branch.
8. Do not delete historical branches until incorporation/supersession is
   evidenced and any preservation requirements have been considered.

## Outstanding GitHub enforcement

The repository contains `scripts/github/merge-policy.json` and the
fail-closed `scripts/github/merge-policy.sh` admin installer. The documented
ruleset requires PR merges, no force pushes/deletion, resolved review threads,
and 12 named CI gates. Its JSON file alone **does not enforce branch protection**.

An administrator must apply and verify that policy using a GitHub token with
`Administration:write`. The existing GitHub integration cannot apply the
ruleset; a repository ruleset inspection and `main.protected` must both
confirm active enforcement before declaring this objective complete.

## Non-goals

This tool does not import code automatically, mutate the remote, run intrusive
OSINT, delete branches or declare that all historical code has been integrated.
Its output is evidence for selecting safe, individually testable ports.
