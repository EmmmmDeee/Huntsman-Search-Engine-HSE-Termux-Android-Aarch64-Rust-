# Continuous evidence normalisation (opt-in)

Huntsman can reconcile configured targets for as long as its serve process remains alive. This Rust thread shares the existing saved-scan store, canonical routing, correlation rules, worker admission and saved-scan analysis endpoint. It does not run a language model or modify source code.

## Configuration

Set HUNTSMAN_CONTINUOUS_TARGETS to a semicolon- or newline-separated list of selectors; for example: example.com;1.1.1.1. Configure HUNTSMAN_CONTINUOUS_INTERVAL_MINUTES=1440 for daily collection. Both are read the way every key is: from ~/.huntsman.env first, then from the environment, so two lines in that file configure the Termux service without exporting anything, and `doctor` and `credential-status` recognise the two names. Start the usual huntsman-recon serve command; a wrong setting ends it before it binds, naming the setting. The Settings tab's Global Settings shows what serve collects and how often ("Continuous normalisation while serve runs"), or that it is off and how to turn it on; the same entry is the `continuous` global of /api/settings.

If targets are not configured, the controller stays off and does not collect remotely. Set HUNTSMAN_CONTINUOUS_TARGETS='*' to continuously re-normalise the most recent saved scan of every canonical target already present in the scan store, without initiating any new network scans. The wildcard may also accompany specific targets, which alone are eligible for recurring collection; people-name targets are refused. At most 32 explicit canonical targets (8192 config bytes) are accepted. Collection interval may be 60 to 10080 minutes, default 1440. Reconciliation wakes every 60 seconds.

Saved scans are kept unchanged in the existing private scans store. For each terminal scan, the shared /api/scans/ID/analyze path recalculates derived findings and writes a bounded, atomic private JSON report to HUNTSMAN_HOME/normalised, or ~/.huntsman/normalised. The deterministic file name hashes the canonical target plus kind; the report carries the source scan ID and limitations.

A bounded revision hint uses the saved scan row and results file metadata (length, nanosecond modification time, and Unix inode when available), and is rechecked around analysis. Reconciliation re-evaluates a saved scan when its revision hint changes, even when its ID is unchanged. A current report now carries `normalisation.state=current` and `source_revision_hint`; refused or modified evidence is marked `normalisation.state=stale` in the current-report slot. The most recent valid previous report is retained separately as `*.previous.json` with `normalisation.state=historical`. Historical findings must not be treated as current findings.

The 60-second revision hint is **not a cryptographic content digest or cross-process transaction**. During each actual analysis, the controller also SHA-256 hashes the bounded saved results before and after the analysis and refuses a current report if the bytes differ; successful reports include `normalisation.results_sha256` and `normalisation.scan_id` for provenance. This detects same-size, restored-mtime edits during analysis without hashing every saved result on every tick. Metadata collisions between ticks, concurrent modification after the final check, and failed writes remain explicit limitations. This is an offline, bounded read of metadata and does not invoke providers or introduce persistent scan duplication.

The passive scan use case and zero recursion depth are used. Other configured provider quotas may still apply. No source failure, failed analysis or missing ancestry is promoted to a verified absence or identity. A refused analysis must not leave the last successful derived report represented as current; the previous report is preserved as historical evidence.

After a completed, aborted or failed scan, collection waits for the full configured interval following its terminal end timestamp (falling back to creation time for legacy rows without an end timestamp); admission failures back off at least 15 minutes. Existing active scans are joined, not duplicated. The scheduler never silently deletes old scans. Once the store reaches its 4096-record capacity, that limit remains observable (`huntsman-recon doctor` warns from 90%); indefinite fresh collection requires an approved retention procedure. `huntsman-recon scans prune --keep N` is that procedure, run by the operator. It lists the ended scans beyond the newest N of each target and lookup, oldest first, and deletes them only with `--apply`, never an active scan, a target's newest, or its newest finished scan. Alert history entries that name a pruned scan keep their scan IDs.

## Retention (opt-in)

Set HUNTSMAN_CONTINUOUS_KEEP=N (1 to 4096, read like the other settings) to have each cycle apply that same plan to the configured targets: after the cycle's alert decisions are recorded, the ended scans of each configured target beyond its newest N are deleted through the scan service, as `scans prune --keep N --apply` would. A cycle whose alert decisions could not be recorded deletes nothing, so a scan an undecided alert still compares against is never removed first. A target's newest finished scan is kept however many failed or aborted scans followed it, because it is the last complete evidence and the next alert's baseline. Scans of targets that are not configured, including every target `*` re-normalises, are the operator's and are never deleted. Each deletion is written to serve's standard error. Unset, the scheduler deletes nothing; any other value stops serve before it binds, naming the setting. The Settings page's continuous entry says how many scans are kept.

## Alerts on recurring collection

For every configured target with at least two finished scans, each cycle decides once whether the newest finished scan raises an alert over the finished scan before it, with the default `scans alert` policy: a new correlation at HIGH risk. Each decision, raised or not, is appended to the alert history beside the saved scans (`alerts.jsonl`), which `huntsman-recon scans alerts`, `GET /api/scans/alerts` and the Web UI's Alerts panel read. The history records the two scan IDs and each reason's risk and rule, never the target or a finding's text. Because the history is the record of what was decided, a restarted serve process does not decide the same scan twice. Deciding reads only saved scans and makes no request. A raised alert is also written to serve's standard error. The wildcard `*` re-normalises without collecting, so it never produces a decision. A decision that cannot be recorded is reported and retried on the next cycle without stopping normalisation.

Set HUNTSMAN_CONTINUOUS_NOTIFY=1 (read like the other two settings) to also post a phone notification through Termux:API's `termux-notification` when a decision raises an alert. Install `pkg termux-api` and the Termux:API Android app and allow its notifications. No root is needed. The notification names only each reason's risk and rule, never the target or a finding's text, because it shows on the lock screen. `0` or unset posts none, and any other value stops serve before it binds, naming the setting. A notification that cannot be posted is written to serve's standard error and not retried: the decision is already recorded, and posting it later would announce the same alert twice. The Settings page's continuous entry says when notifications are on.

## Lifecycle

READ CONFIG -> CANONICALISE -> READ SCAN STORE -> SELECT LATEST SCAN PER CANONICAL TARGET -> DECIDE ALERTS FOR NEWLY FINISHED SCANS -> DELETE ENDED SCANS BEYOND THE KEPT (WHEN CONFIGURED) -> ANALYSE COMPLETED SCANS -> ATOMICALLY SAVE DERIVED REPORT -> CHECK RECENCY AND RETRY WINDOWS -> START OR JOIN DUE SCANS -> SLEEP 60 SECONDS -> REPEAT.

This is an evidence normalisation and refreshing controller, not an unattended software-editing agent. It cannot ensure that providers respond or that the Termux process keeps running. Android may suspend a background Termux server; see docs/INSTALL.md. Service restarts derive cadence from saved scan timestamps.

## Verification

Run cargo fmt --check, cargo run --locked -p xtask -- gate full, huntsman-recon doctor serve and huntsman-recon scans list --json. Compare each normalised report's scan ID with the durable scan store and inspect source outcomes. Before merge, install the exact-head Android aarch64 prebuilt on a no-root Termux handset, exercise the loopback web UI, observe a new normalised report, restart the service and verify the report and source scan provenance persist.
